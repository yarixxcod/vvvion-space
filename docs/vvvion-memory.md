# VVVion Memory — архитектура и контролируемый выпуск

Рабочая ветка: `feature/vvvion-memory`, PR в `uiux-polish-3.0.1`. Начальная разработка выполнена без изменения Production. Новые таблицы проверены только на изолированном PGlite. Production-миграции и пользовательские данные на этапе разработки не менялись.

## Хранение и совместимость

Используются существующие Better Auth `user.id`, `authMiddleware`, PostgreSQL-клиент `getSql`/`withTransaction` и центральный AI proxy. Новых пользователей, истории чатов, провайдеров или отдельной базы не создаётся.

- `user_memory_settings`: включение использования, отдельное согласие на автоизвлечение, поколение настроек.
- `user_memories`: факты, категория, источник, уверенность, важность, срок, статус, версия, даты и ссылка на существующего пользователя.
- `user_memory_chats`: исключённые диалоги владельца.
- `user_memory_blocks`: только отпечатки отдельно удалённых фактов, запрещающие их повторное автоизвлечение.
- `user_memory_events`: операция, результат, задержка и числовые показатели; без фактов, промптов, ответов и текстов ошибок.

Все записи принадлежат аккаунту, а не модели. Обычные модели, персонажи и новые модели через существующий router получают одинаковый механизм отбора. SSE-формат ответов не изменён. Android WebView использует тот же сайт и API; отдельный APK не изменялся. Старые клиенты без новых метаданных получают релевантную память после серверной проверки аккаунта, но **не запускают автоизвлечение или команды**. Для нативного клиента с собственной отправкой нужен самостоятельный этап добавления полей `memoryInput`.

Telegram использует уже проверенную привязку аккаунта, не имя или username. Память доступна в существующем AI-режиме после выбора модели; новый отдельный режим Telegram-управления настройками не добавлялся. Команды подтверждаются сервером, а обычные ответы продолжают использовать существующий provider router.

Прежние ручные заметки браузера сохранены без изменения поведения, когда функция недоступна. При новом режиме они не передаются параллельно в AI-контекст; доступен перенос по одной заметке после просмотра пользователем. Автоматического импорта личных данных нет.

## API

Это TanStack Start server functions, а не новые открытые REST endpoints. Идентификатор владельца поступает только из проверенной сессии; переданный клиентом `userId` не используется.

| Функция | Метод | Данные |
| --- | --- | --- |
| `getMemoryWorkspace` | GET | Необязательный `chatKey`; собственные настройки и записи |
| `updateMemorySettings` | POST | `enabled`, `automatic`, отдельное `consent` при включении автоизвлечения |
| `saveUserMemory` | POST | Содержимое, категория, необязательные id/version, срок, отдельное sensitive-согласие, подтверждение конфликта |
| `deleteUserMemory` | POST | Собственные id + version |
| `clearUserMemories` | POST | Явное `confirm: CLEAR_MEMORY`; также приостанавливает автоизвлечение |
| `exportUserMemories` | GET | Собственные факты и настройки в JSON |
| `setMemoryChatPolicy` | POST | `chatKey`, `disabled`; чужой сохранённый чат запрещён |
| `getMemoryAdminStats` | GET | Только администратор; агрегаты без фактов |

## Извлечение, команды и поиск

Извлечение намеренно консервативное и **без вызовов LLM**. Поддерживаются ясные русские конструкции от первого лица: имя/обращение, стиль и язык ответов, проекты, интересы, основной язык программирования, используемые технологии, устройства и цели; несколько английских конструкций. Пример: «Я разрабатываю VVVion Space на React». Максимум два кандидата из одного прямого сообщения, уверенность 0.95. Это не семантическое понимание произвольного разговора: необычные формулировки могут быть пропущены. Их можно сохранить явной командой или вручную. Принятые решения по проекту также сохраняются вручную/командой, без вывода из ответа модели.

Сегодняшние события, неопределённые предположения, цитаты, код, документы, вложения, ответы модели и чувствительные данные не сохраняются автоматически. Явные команды распознаются только как самостоятельное прямое сообщение. На сайте сервер сверяет `memoryInput.text` с последним user-сообщением и требует `attachments: false`. Метаданные клиента не дают новых прав: владелец всегда определяется сессией. У старых клиентов этот путь закрыт.

Рабочие команды:

- `Запомни, что я люблю Python` — фактическое сохранение до ответа пользователю.
- `Что ты обо мне помнишь?` — собственные активные факты, максимум 20 в ответе; остальные в настройках.
- `Забудь, что я люблю Python` — точное совпадение или единственное совпадение по подстроке; при неоднозначности запрос уточнения.
- `Обнови память: старый факт => новый факт` — версия проверяется сервером. Ваговое «Обнови информацию о моём проекте» запрашивает конкретику.
- `Не запоминай этот разговор` — запрещает и чтение, и запись в текущем сохранённом диалоге; старые факты не удаляет.
- `Верни память в этот диалог` — снимает исключение, общий переключатель сохраняет приоритет.

Без сохранённого идентификатора диалога сервер честно просит открыть сохранённый чат или использовать настройки. Чувствительные факты командой не сохраняются: нужен отдельный checkbox на конкретной записи в настройках.

Дубликаты: нормализация Unicode, пробелов, регистра, ё/е и нескольких синонимичных вводных интересов; уникальный отпечаток на владельца. Семантически разные перефразировки могут остаться отдельными фактами. Противоречия распознаются для устойчивых слотов (имя, основной проект, язык, устройство и т.п.); кандидат получает статус `conflict` и не участвует в ответах до подтверждения замены. Это не универсальный поиск логических противоречий в произвольном тексте.

Поиск — лексическое ранжирование максимум 120 собственных записей, с приоритетом обращения/стиля и проектов при техническом вопросе. Неактивные и просроченные исключены. Векторная инфраструктура не нужна для такого объёма; морфология/семантические синонимы пока ограничены. Выбираются максимум 8 фактов; итоговый блок фактов со служебным заголовком ограничен **1800 UTF-8 байтами** (консервативная граница токенного бюджета). Длинный факт, не помещающийся вместе с заголовком, пропускается. Отдельная короткая служебная инструкция запрещает модели обещать операции памяти от своего имени.

Блок сериализован как данные; явно запрещено исполнять содержащиеся в нём инструкции или смешивать биографию персонажа с пользователем. Фильтр дополнительно отвергает очевидные попытки изменения системных правил. Это снижение риска prompt injection, а не доказательство невозможности обхода любого LLM.

## Защита, гонки, задержки и цена

- Проверка сессии, блокировки аккаунта, владельца и feature allowlist; SQL параметризован.
- Поля source/confidence/importance задаёт сервер. Запись 3–500 символов, максимум 120 записей; 60 событий изменения/извлечения в час на владельца. Активные ошибки тоже попадают в этот счётчик; чтение отдельно не лимитируется памятью и использует ограничения существующей платформы.
- Обновление/удаление требуют текущую версию. Все изменения сериализованы блокировкой настроек владельца. Поколение инвалидирует задания, запущенные до отключения, удаления или изменения режима. При конкуренции двух фоновых задач с одним поколением одна может быть консервативно пропущена.
- Отдельное удаление физически удаляет строку, оставляя только блокирующий отпечаток. Явное повторное ручное добавление снимает блокировку. Очистка физически удаляет факты и отпечатки и выключает автоизвлечение; старые задания не восстановят данные.
- Секреты/ключи/токены/платёжные реквизиты отбрасываются до записи, даже при sensitive-согласии. Фильтр эвристический: не следует вводить замаскированные или неизвестные ему секреты; он не заменяет DLP всех возможных форматов.
- Чувствительные данные — только вручную с отдельным согласием для записи. При использовании памяти релевантные факты передаются выбранному пользователем AI-провайдеру; это указано в интерфейсе.
- Чтение имеет statement timeout 300 мс и общий deadline 450 мс; при ошибке/таймауте чат идёт без новой памяти. Уже начатый запрос может завершиться в фоне. Записи имеют statement timeout 1500 мс на SQL statement; сетевой сбой/ожидание подключения ограничиваются существующим DB-клиентом.
- Автоизвлечение запускается через существующий `keep`/Vercel `waitUntil`, не блокируя начало ответа. Это best effort без отдельной гарантированной очереди; прерывание процесса может пропустить факт. Платного резервного вызова нет, стоимость извлечения — 0 вызовов LLM. Дополнительный контекст может увеличить обычную стоимость ответа выбранной модели.
- Нет plaintext-кэша, глобальной базы пользовательских фактов или обучения моделей. Телеметрия хранится 30 дней и очищается при следующих изменениях владельца; при полной недоступности базы ошибки не всегда удастся посчитать.
- Админ видит включённых пользователей, число записей, среднее по владельцам записей, ошибки/задержку и вызовы/$ за 30 дней. Не фактографию и не историю переписки. Фактическая биллинговая стоимость обычных ответов не относится к этим метрикам извлечения.

Удаление новой памяти не переписывает существующую историю чатов и уже переданный провайдеру контекст. Резервные копии хостинга могут сохраняться некоторое время; реальный retention следует проверить в настройках хостинга перед выпуском. Значение не выдумывается в UI. Для удаления истории/аккаунта действуют существующие механизмы продукта; новые таблицы имеют FK cascade.

## Безопасное включение — только после отдельного разрешения

1. Проверить PR, состояние актуальной целевой ветки, резервные копии и доступность БД. На staging с отдельной БД применить `0056_vvvion_memory.sql` штатным migration runner в транзакции; повторная миграция должна быть пустой. Проверить rollback на копии, не production.
2. После отдельного разрешения применить ту же additive-миграцию штатным runner в Production. **Не запускать весь `npm run build` ради проверки:** он вызывает `db:migrate`. Для проверки без миграций использовать `npm run build:web`.
3. Выпустить согласованный код с `VVVION_MEMORY_ENABLED=false` или без переменной. Пользовательская и автоматическая память новой системы выключены. При выключенном флаге центральный AI-слой не делает запросов к новым таблицам.
4. Для одного тестового аккаунта поставить серверные переменные `VVVION_MEMORY_ENABLED=true`, `VVVION_MEMORY_USERS=<точный существующий user.id>`. Не username и не email. Пустой allowlist не открывает доступ никому. `*` означает явный доступ всем и нужен только на последнем этапе.
5. Войти тестовым аккаунтом, включить память, отдельно согласиться на автоизвлечение. Проверить настройки, реальные команды и новый диалог с другой моделью; Telegram — только с уже привязанным аккаунтом. Проверить обычный streaming, ограничения, профиль и прочие модули.
6. Проверить ошибки, задержки, число записей и согласия. Расширять allowlist постепенно. Перед all-users оценить нагрузку, провайдерные условия хранения и качество извлечения на согласованных тестовых примерах.

`vercel.json` специально отключает Git deployment для `feature/vvvion-memory`: это защищает от обычного auto-build, который в текущем проекте вызывает миграции. Перед любым дальнейшим выпуском оператор должен осознанно выбрать утверждённую ветку/коммит и сценарий миграции. Эта настройка не блокирует ручной CLI deployment и не является заменой политике доступа Vercel.

## Откат

Быстрый откат: `VVVION_MEMORY_ENABLED=false`, пересоздать/перезапустить deployment согласно правилам платформы. Новые функции перестают читать и писать память; прежний чат/локальные заметки остаются. Данные сохраняются для разбора, а jobs дополнительно перепроверяют флаг перед записью. Не выполнять destructive rollback для устранения обычного сбоя.

При необходимости вернуть предыдущий код — оставить новые таблицы: они не мешают старой версии. Полное удаление схемы — отдельная согласованная операция после выгрузки данных, отключения флага и завершения старых фоновых работ. `migrations/down/0056_vvvion_memory.sql` удаляет только пять новых таблиц; это необратимо без резервной копии. Если после этого потребуется повторно применить миграцию, согласованно убрать только её запись из `_migrations`, иначе штатный runner считает её выполненной. Никакой автоматизации этого destructive шага нет.

### Подготовка разрешённого Production-выпуска

После отдельного указания владельца «если всё отлично, пуш в прод» подготовлен первый выпуск кода с `VVVION_MEMORY_ENABLED=false`. Для него используется `npm run build:web`: production migration runner не запускается, новые таблицы остаются подготовленными к будущему контролируемому включению. Не включать память до согласованной миграции и проверки тестового аккаунта.
